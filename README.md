# Adaptation Insights: grey literature extraction pipeline

This is the code behind the grey literature workstream of Adaptation Insights
(CGIAR, WP2 Evidence Synthesis). The workstream asks one question: which
climate adaptation actions have actually been carried out in Africa's food
and agriculture sector, and with what results? The answer is built from
project evaluation documents published by six funders: the World Bank, the
Global Environment Facility (GEF), the Green Climate Fund (GCF), the African
Development Bank (AfDB), the Adaptation Fund and the Climate Investment
Funds (CIF).

The pipeline finds these documents, removes duplicates, decides which ones
are in scope, catalogues them in a shared Zotero library, reads each one with
a language model, checks every extracted value against the page it came
from, maps the values to the project's controlled vocabularies, and scores
the result against a gold set extracted by hand.

Everything is written in R. Each step is one script, and the scripts sit in
folders numbered in the order the work happens.

Contact: Lolita Muller, Alliance Bioversity International and CIAT
(M.Lolita@cgiar.org).

## 1. What the pipeline does

The work runs in nine steps. Each step has its own folder under `R/`.

| Step | Folder | What happens |
|---|---|---|
| 1 | `R/01_retrieve` | One scraper per funder downloads evaluation documents and writes a metadata list. Files that teammates add to Zotero by hand are pulled into the corpus too. |
| 2 | `R/02_dedup` | Every file gets a census row: what kind of document it is (its family), which project and report identifiers it carries, its checksum. Copies of the same document are moved to a duplicates folder with a register. |
| 3 | `R/03_screen` | A model reads each document and says whether it is in scope under the project protocol: an evaluation of a climate adaptation action in African agriculture, published 2015 to 2025. Code rules then check the model's answer. Unsure cases go to a person. |
| 4 | `R/04_catalogue` | Every judged document becomes a record in the shared Zotero library, in its funder's included, to screen or screened out collection, with the file attached. |
| 5 | `R/05_extract` | Session 1: the model reads an in scope document and returns exact quotes, numbers and page references for each field of the template. Code checks every value against the cited page. |
| 6 | `R/06_harmonise` | Session 2: the verified extracts are mapped to the template's controlled vocabularies (actors, locations, intervention types, result levels). Rules first, one batched model call for what is left. |
| 7 | `R/07_review` | Anything the pipeline could not decide (a new actor, a new location, a new vocabulary term) is audited and put in a list for the team. |
| 8 | `R/08_quality` | The output is scored field by field against the ten gold projects and a ten document holdout set. |
| 9 | `R/09_publish` | Results are exported in the shape of the template, with costs, prompt history and the workflow figure. |

The one page picture of this workflow is `Workflow_diagram.docx` in the
`01_Protocol` folder next to the repo (see section 2).

## 2. What is in this repo and what is not

The repo holds code and the small reference tables the code reads at run
time. It does not hold documents, model outputs, or team documents.

| In the repo | Not in the repo |
|---|---|
| `R/` all scripts | The corpus of PDFs (about 930 files, on OneDrive under `03_Documents`) |
| `catalogues/` metadata lists per funder, the gold standard, decision caches | Run outputs and caches (`outputs/`, ignored by git, regenerated by the scripts) |
| `docs/AI_Extraction_Protocol.md` the extraction protocol text | Team documents: protocol Word files, the extraction template, the QC question list, the knowledge base (`00_Knowledge`, twelve short explanatory notes) |
| `CLAUDE.md` and `.claude/` working rules for AI coding sessions | API keys (`.Renviron`, ignored by git) |

On the project's OneDrive the repo is the folder `07_Pipeline`, and the
scripts expect its neighbours to be there:

```
Grey Literature/
  00_Knowledge/            what the project is, how it works, what is open
  01_Protocol/             protocol, workflow diagram, document families, QC questions
  02_Template/             the extraction template (Excel) and its readme sheet
  03_Documents/            the corpus: one folder per funder, plus pilot/ and duplicates/
  05_Extraction_Results/   what people open: results, review lists, scores
  07_Pipeline/             this repo
```

`R/00_shared/paths.R` is the single place that knows this layout. Every
script finds the repo root from its own location, two levels up, and the
project root one level above that. If you clone the repo elsewhere, point
`GL_ROOT` in `paths.R` at a folder with the same neighbours.

Each scraper starts with a header block naming the source, the URL, the
strategy, the document types and the site's quirks. All requests go through
one polite fetcher with delays, every failure is caught and logged, and every
PDF is checked before it is kept. Each scraper writes a metadata list with at
least these columns: id, title, pdf_url, doc_date, doc_type, country,
project_id, web_url.

### R/02_dedup: one document, one record

| Script | What it is |
|---|---|
| `doc_census.R` | One row per file in every scanned folder: family, kind, project and report identifiers found on the cover, checksum, cover text. Cover pages are cached, so `--redetect` re-runs the family rules in seconds after a rule change. `--refresh` rereads the files, `--source=` limits the run to one funder. |
| `dedup_corpus.R` | Finds identical files and the same document filed twice (same family, same kind, same identifier). Reports first; `--apply` moves the extra copies to `03_Documents/duplicates/` and writes an Excel register saying which copy was kept and why. Projects with several documents (a mid term review and a terminal evaluation, say) are listed for a protocol decision, not moved. |

### R/03_screen: is this document in scope?

| Script | What it is |
|---|---|
| `screen_scope.R` | The screener. Reads the whole document and returns a verdict (in scope, out of scope, unsure), the reason, the criterion that failed, quotes that evidence the climate risk and the intervention, the document kind, the publication year and the family. Resumable. `--source=` one funder, `--limit=` a test run, `--out=` and `--shard=k/n` for parallel runs, `--reask=` to re judge a list. |
| `screen_rules.R` | Code checks on the verdicts: the 2015 to 2025 window is applied here from the model's own verdict, so moving the window is a two number change and a rerun with no document read again; in scope with no climate risk quoted becomes unsure; a project the model itself calls mitigation goes out; a programme evaluation covering several projects becomes unsure; bare one word reasons are listed for a re ask; documents of one project with conflicting verdicts are listed. A person's decisions in `scope_screen_overrides.csv` win over everything. Writes the unsure queue for a person. |
| `merge_screen_parts.R` | Folds parallel shards back into the one screening file. Newest wins. |
| `screen_corpus.R` | Older sweep that checked folder labels against document contents. Kept for reference. |

### R/04_catalogue: Zotero and the metadata index

| Script | What it is |
|---|---|
| `zotero_upload.R` | The sync. Builds one record per document from the funder metadata lists, lets the screening decide membership and status (`zotero_from_screening.R`), creates and patches records in the group library, uploads the files, moves duplicates to their own collection (`zotero_duplicates.R`) and places hand added files under their records (`zotero_adopt_pulled.R`). Idempotent: run it again and nothing is created twice. |
| `zotero_from_screening.R` | The join between the screening file and the metadata pool. In scope becomes included, unsure becomes to screen, out of scope becomes screened out. |
| `zotero_duplicates.R` | Records of files the dedup step moved out go to the funder's duplicates collection. |
| `zotero_adopt_pulled.R` | A file a teammate dropped into Zotero, once screened, is attached to the record created for it. Nothing is deleted. |
| `zotero_tidy_attachments.R` | Records that hold the same PDF twice keep the oldest copy; the others go to Zotero's trash, where they can be restored. `--dry` lists. |
| `zotero_dedup_report.R` | A standing report of probable duplicate records in the library. |
| `build_doc_index.R` | One index from corpus filename to catalogue metadata (title, project id, year, report number, URL). The extraction uses it to prefill fields, because a catalogue value beats an extracted one. |
| `sync_metadata.R` | Refreshes `catalogues/` from the metadata lists that live next to the documents. |
| `corpus_inventory.R` | The census workbook `03_Documents/Corpus_Inventory.xlsx`: per source counts from the screening file, one sheet for the strict agriculture rule and one for the scenario where documents put out on a linked sector (water, forestry and conservation, coastal, social protection, land) come in, plus folder and file listings and Zotero presence. |

Zotero fields: Report Number holds the document's own number where the
funder gives one (a World Bank ICR number, say). Call Number holds the
project identifier (World Bank P code, GEF id, AfDB project code, GCF FP
code), because Zotero has no project number field. Tags carry the family,
the screening verdict and an internal document tag that makes the sync
idempotent.

### R/05_extract: Session 1, the document's own words

| Script | What it is |
|---|---|
| `extract_verbatim.R` | Reads one PDF or a manifest of PDFs. For each field group (identity, geography, rationale, results, finance) it sends the page tagged document and asks for exact quotes, literal values and page numbers. Then code checks each value against the cited page: found, found on another page, or not found. Values that fail are dropped. Loads the family module for the document. |
| `families/` | One module per document family: which pages hold which fields, how the results table is laid out, what to ignore. `wb_icr.R`, `afdb_pcr.R`, `agency_evaluation.R`, `gef_portal_form.R`, `gcf_completion.R`, `cif_country_me.R`, `programme_evaluation.R`, `generic.R`. |
| `extract_locations.R` | Session 1 for the location specific sheet of the template: one row per named location and intervention. |
| `run_corpus.R` | Resumable driver over the corpus. Takes only documents the screening judged in scope. `--dry` plans and prices the run, `--source=` and `--family=` narrow it, `--limit=` tests it, `--all` ignores the verdict. |

How a long document is handled: the family module says which sections hold
template fields, so the model sees those pages with their original numbers.
A near empty first page (a picture cover) triggers one small vision call to
read the title. Pages that hold an indicator table are also sent as images,
because table text scrambles when extracted. Durations, dates, administrative
counts, disbursement amounts and methodology numbers can never fill a results
slot; that is decided in code, not by the model.

### R/06_harmonise: Session 2, the template's words

| Script | What it is |
|---|---|
| `harmonize.R` | Sees only the verified extracts, never the documents. Maps each to the template's controlled vocabulary using the template readme definitions. Rules first, then one batched model call for what remains. Every decision is written to `catalogues/vocab_decisions.csv` and reused, so reruns are identical and cost almost nothing. When no value fits, the answer is NOT STATED and the cell stays empty; a term the vocabulary lacks is logged as a candidate, never written into the data. |
| `harmonize_locations.R` | The same for the location sheet: location codes, subsector, target beneficiary, result level. |

### R/07_review: what the pipeline could not decide

| Script | What it is |
|---|---|
| `audit_proposed_actors.R` | Every organisation the pipeline could not match to the actor registry gets a verdict (probably new, probably a known actor under another name, probably noise) before a person reads the list. |
| `audit_proposed_locations.R` | The same for locations, checked against the location registry. |
| `audit_reference_targets.R` | Finds numbers the manual reference recorded as results that are in fact targets. |
| `build_actor_synonyms.R`, `check_actor_synonyms.R` | Build the synonym table for organisation names and prove that no synonym points at two institutions. |
| `check_actor_countries.R` | Writes every national body in the registry the ways a document would (with its country, in capitals, by acronym, without the country) and checks the matcher resolves each to the right code. Run after a registry or matcher change. |
| `harvest_actor_websites.R` | Reads one page of each organisation's own site to learn how it names itself. |

### R/08_quality: how good is it

| Script | What it is |
|---|---|
| `score_pilot.R` | Field by field agreement between the pipeline and the gold set for the ten gold projects, with a column saying why each disagreement happened. |
| `compare_results_slots.R` | Puts the three result slots of two Session 1 runs side by side, document by document, marks the slots that are reference values, and counts hits and documents with a people count first. Used to judge the headline results rule. |
| `test_regressions.R` | Regression tests. Every fault that once produced a wrong value is a case here (a country name found inside another name, a ministry coded to the wrong country, money printed in scientific notation, a budget note computed from the wrong number). | `score_locations.R` | The same for the location sheet against the manual location rows. |
| `reference_comparison.R` | One workbook that puts a reference extraction, the pipeline's rows and the scorer's verdicts side by side: summary by field and document, every check, mismatches shaded. Takes the score, reference and harmonised CSVs as arguments. |

The gold set (projects P001 to P010) may be used to tune prompts. The holdout
set (H001 to H010, ten corpus documents) is never looked at while tuning, so
its score is the honest one.

## 4. Ideas the code is built on

**Deterministic first, model second.** If a pattern, a table read or a
lookup can decide, no model call is spent. Where a model is needed, calls are
batched and the answers are cached.

**Everything a model extracts carries a page number and is checked against
that page.** Session 1 returns the document's own words. Code string matches
every quote, number and name against the cited page. A value that is not
found is dropped, not kept. No fabricated quote has been observed across the
measured runs.

**Two sessions, not one.** Reading the document and choosing a vocabulary
value are separate jobs. Reading is expensive and done once. Choosing is
cheap and can be redone whenever the vocabulary changes, without opening a
document again.

**A source is not a family.** The same funder publishes several kinds of
document, and the same kind appears under several funders. Extraction is
routed by the document family, recognised from the first pages, not by the
folder the file sits in. Families are defined once, in
`R/00_shared/doc_families.R`.

**Results tables are read as tables.** In a results framework, the figures
define the columns and the header words say what each column means
(baseline, target, achieved). The code never picks a value by its position
on the page or by how big it is.

**The pipeline proposes, the team decides.** New actor codes, new location
codes and new vocabulary terms are written to review lists, never added
silently. Screening verdicts a person changes are recorded in an overrides
file that wins over the rules.

**Nothing is lost.** Documents are never deleted, only moved to a duplicates
folder with a register. Every screening decision is kept beside the model's
original verdict. Zotero holds every document in a collection that says what
was decided. A new criterion means rerunning the rules, not starting over.

**The gold set is for tuning, the holdout is for measuring.**

## 5. Document families

The family says how a document is written, and therefore where each template
field sits and how its tables are laid out. Seventeen families are defined.
Progress documents (marked progress) report on an ongoing project and are
screened out by rule, because the protocol wants evaluations.

| Family | What it is | Extraction module |
|---|---|---|
| `wb_icr` | World Bank Implementation Completion and Results Report | `wb_icr` |
| `wb_icrr` | World Bank IEG review of an ICR | `agency_evaluation` |
| `wb_isr` | World Bank Implementation Status Report (progress) | none |
| `afdb_pcr` | AfDB project completion report form | `afdb_pcr` |
| `afdb_pper` | AfDB project performance evaluation report | `agency_evaluation` |
| `gef_portal_form` | GEF Portal terminal evaluation or mid term review form | `gef_portal_form` |
| `unep_completion_form` | UNEP operational completion form | `gef_portal_form` |
| `gef_pir` | GEF project implementation report (progress) | none |
| `gef_indicator_sheet` | GEF-7 core indicator worksheet | none |
| `gcf_completion_summary` | GCF project completion summary | `gcf_completion` |
| `gcf_pcr` | GCF project completion report | `gcf_completion` |
| `af_ppr` | Adaptation Fund project performance report (progress) | none |
| `cif_country_me` | CIF country monitoring and evaluation report, covers several projects | `cif_country_me` |

## 6. Setting up

**R.** Version 4.4 or later. Install the packages once:

```
Rscript R/00_shared/install_packages.R
```

The packages are httr, rvest, xml2, jsonlite, curl and fs for retrieval;
pdftools and qpdf for reading PDFs; dplyr, purrr, tibble, tidyr, stringr,
readr, lubridate and glue for data handling; openxlsx and readxl for Excel;
ellmer for model calls; cli for console output. One scraper
(`worldbank_project_info.R`) drives a headless browser and also needs
chromote and processx; install those only if you run it.

**Keys.** Put these in an `.Renviron` file in your R home folder. On the
project machine that is the OneDrive redirected Documents folder; the newer
scripts also look there when the variable is missing.

```
OPENAI_API_KEY=...         # screening, extraction, harmonisation
ZOTERO_API_KEY=...         # the group library
ZOTERO_LIBRARY_ID=...      # group id
ZOTERO_LIBRARY_TYPE=groups
```

Optional: `EXTRACT_MODEL`, `SCREEN_MODEL` and `HARMONIZE_MODEL` override the
model each script uses (the defaults, set at the top of each script, are
gpt-5-mini for extraction and harmonisation and gpt-5-nano for screening);
`EXTRACT_OUT_DIR` redirects run outputs.

**Folders.** The scripts expect the OneDrive layout in section 2. Nothing
needs to be configured if the repo sits in `07_Pipeline` next to
`03_Documents` and `05_Extraction_Results`.

**Windows note.** Some corpus paths are longer than 260 characters. The
scripts handle this themselves; if you open a file another way, use the
`\\?\` prefix or copy it to a short path first.

## 7. Running the pipeline

From the repo root, one script per step. Every script's header says what it
reads, what it writes and which flags it takes.

```
# 1 retrieve
Rscript R/01_retrieve/run_all.R                       # all working scrapers
Rscript R/01_retrieve/zotero_pull.R --dry             # files added to Zotero by hand

# 2 dedup
Rscript R/02_dedup/doc_census.R                       # family, ids, checksum per file
Rscript R/02_dedup/dedup_corpus.R                     # report; add --apply to move copies

# 3 screen
Rscript R/03_screen/screen_scope.R --source=gcf       # the screener, resumable
Rscript R/03_screen/merge_screen_parts.R              # only after parallel shards
Rscript R/03_screen/screen_rules.R                    # code rules, overrides, unsure queue

# 4 catalogue
Rscript R/04_catalogue/build_doc_index.R
Rscript R/04_catalogue/zotero_upload.R                # sync the library to the verdicts

# 5 and 6 extract and harmonise
Rscript R/05_extract/run_corpus.R --dry               # plan and price; drop --dry to run
Rscript R/06_harmonise/harmonize.R                    # newest Session 1 output

# 8 and 9 score and publish
Rscript R/08_quality/test_regressions.R               # regression cases, run before harmonising
Rscript R/08_quality/score_pilot.R                    # against the gold set
Rscript R/09_publish/export_results.R                 # workbooks into 05_Extraction_Results
Rscript R/09_publish/cost_report.R
```

A single document or a small manifest can be extracted directly:

```
Rscript R/05_extract/extract_verbatim.R path/to/document.pdf
Rscript R/05_extract/extract_verbatim.R manifest.csv     # columns project_code, pdf, focus
```

Costs, as measured: screening the whole corpus of about 900 documents costs
about one US dollar with gpt-5-nano. Session 1 extraction costs a few cents
per document with gpt-5-mini; the five calls for one document share the same
document text, and that shared prefix is priced at a tenth by the provider.
Keep every per call instruction after the document text, or the bill roughly
doubles.

## 10. Growing the pipeline

**A new funder.** Write a scraper in `R/01_retrieve` following the header
and column conventions above (`.claude/skills/new-scraper` walks through
it). Add the source and its folders to `paths.R`. Everything downstream works
as is: census, dedup, screening, Zotero, extraction by family.

**A new document family.** Add one entry to `R/00_shared/doc_families.R`
(label, detection words, module) and one module in `R/05_extract/families/`
if the existing ones do not fit. Run `doc_census.R --redetect` to reclassify
the corpus from the cached covers.

**A wider timeframe** (documents from 2000, say). Change the two year
constants in `screen_rules.R` and rerun it. No document is read again,
because the model's verdict is stored separately from the year rule. Then
rerun the Zotero sync and the extraction driver.

**A new screening criterion.** Add the rule to `screen_rules.R`, or change
the screener prompt in `screen_scope.R` and re ask the affected documents
with `--reask=`. All earlier decisions stay in the screening file.

**A template change.** Session 2 (`harmonize.R`) is rerun against the new
vocabulary at almost no cost. Decisions taken under the old vocabulary
retire on their own, because each is keyed to a fingerprint of the option
list. Session 1 is rerun only if a new field needs new evidence from the
documents.

## 11. Conventions

- Plain language in every document and every script header. No em dashes.
- Every script starts with a header saying what it does, what it reads, what
  it writes and which flags it takes.
- Every script finds the repo root from its own path, two levels up, so
  scripts stay two levels below the repo root.
- Extraction never writes into `03_Documents`. Only the dedup and catalogue
  steps move or file documents.
- Commits follow the conventional style: `feat:`, `fix:`, `docs:`,
  `refactor:`.
- Team documents that a person has edited are added to, never regenerated.
